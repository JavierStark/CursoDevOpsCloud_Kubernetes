07 Conceptos core

Desired State
Reconciliation

K8s nunca para de comparar el estado actual con el deseado. Cuando difieren, actúa.

replicas: 3 # desired
running: 2 # actual
→ crea 1 Pod nuevo
OBSERVE — el controller lee el estado actual del cluster
DIFF — compara con el estado deseado (spec)
ACT — toma la acción mínima para convergir
Desired State (spec)
replicas: 3
↕
Controller Manager
OBSERVE → DIFF → ACT
↕
Actual State
running: 2
→ Crea 1 Pod nuevo
08 YAML

Anatomía de un YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: default
  labels:
    app: my-app

spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    spec:
      containers:
        - name: app
          image: nginx:1.25

status:
  readyReplicas: 3
  updatedReplicas: 3
metadata Identidad del recurso: nombre, namespace, labels, annotations. Todo lo que lo identifica y clasifica.
spec Estado deseado — lo que tú defines. K8s intentará hacer que el mundo se parezca a esto.
status Estado actual — gestionado y escrito por K8s. Solo lectura para nosotros.
Siempre presentes en todo recurso K8s:
apiVersion · kind · metadata · spec

16 Health Checks

Liveness vs Readiness

livenessProbe
❓¿Está vivo el proceso?
💀Fallo → K8s reinicia el contenedor
restart: CrashLoopBackOff posible
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
readinessProbe
❓¿Listo para recibir tráfico?
🚫Fallo → K8s saca del Service (no reinicia)
status: Running but not Ready
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
17 Ejercicio práctico
Lab 04 Running pero Not Ready 
# 04-readiness-probe.yaml
apiVersion: v1
kind: Pod
metadata:
  name: not-ready-pod
spec:
  containers:
    - name: app
      image: nginx:1.25
      readinessProbe:
        httpGet:
          path: /nonexistent
          port: 80
        initialDelaySeconds: 2
        periodSeconds: 3
Qué observar
applykubectl apply -f 04-readiness-probe.yaml
estadokubectl get pod not-ready-pod
Output esperado:
NAME           READY  STATUS
not-ready-pod  0/1   Running
Pod Running pero 0/1 Ready → excluido del Service. El proceso está vivo pero la readiness probe falla.

19 Ejercicio práctico
Lab 05 ConfigMap para frontend 
# 05-configmap-frontend.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-config
data:
  API_URL: "https://backend-svc:8080"
  FEATURE_DARK_MODE: "true"
  MAX_ITEMS: "50"
---
apiVersion: v1
kind: Pod
metadata:
  name: frontend-pod
spec:
  containers:
    - name: frontend
      image: nginx:1.25
      envFrom:
        - configMapRef:
            name: frontend-config
Verificar inyección
applykubectl apply -f 05-configmap-frontend.yaml
verificar CMkubectl describe cm frontend-config
verificar Podkubectl exec -it frontend-pod -- env | grep API
actualizarkubectl edit cm frontend-config# Pod necesita reinicio para ver cambios
Pro tip
Usa envFrom.configMapRef para inyectar todas las claves de golpe.
Ejercicio Final

Despliega una app
completa

Combina todo lo aprendido: Deployment + Service + ConfigMap + Probes. El reto final integra los 5 conceptos del taller en un único flujo de despliegue.

01 · ConfigMap Crea un ConfigMap con las variables de entorno de tu app kubectl apply -f configmap.yaml
02 · Deployment Despliega la app con 3 réplicas, probes y referencia al ConfigMap kubectl apply -f deployment.yaml
03 · Service Expón el Deployment con un ClusterIP y accede vía port-forward kubectl apply -f service.yaml
04 · Escalar Sube las réplicas a 5 y observa el rolling update kubectl scale deploy app --replicas=5
05 · Romper & Arreglar Introduce un error a propósito y diagnostica con describe + logs kubectl describe pod <name>
06 · Rollback Haz rollback a la versión anterior y verifica el historial kubectl rollout undo deploy app
